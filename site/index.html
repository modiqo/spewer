Spewer: Stop Spending Frontier Tokens on Routine Work

I built a local delegation service so Codex can send bounded work to Luna or Qwen3—and give me a durable receipt without making me leave Codex.

For months, I paid frontier-model prices for work that did not require frontier-model judgment. I built Spewer so my preferred harness can hand routine work to a cheaper worker.

I am comfortable in Codex and Claude Code. Their interfaces, context handling, tools, and subscriptions fit how I work. Open harnesses such as OpenCode and Pi make model choice a first-class feature, but switching harnesses was not the problem I wanted to solve.

My default stack is Codex, so I reached for GPT-5.6 Sol at high or xhigh reasoning. That made sense for architecture, unfamiliar systems, and hard debugging. It made less sense for repository scans, summaries, test inventories, and other bounded tasks.

The convenience tax was subtle: one interface made every prompt look like a frontier prompt. I needed a delegation boundary inside the workflow I already liked.

Delegate began as my private escape hatch

Luna changed the shape of the problem because it handled simple work quickly and cheaply enough to be useful. I started an internal project named delegate to send it repetitive tasks.

The first version was literal. I kept the hard problem in Codex, projected a smaller objective, and asked Luna to return the result. That saved frontier attention, but it exposed the systems work hidden inside the word “delegate.”

A useful delegation needs more than a model switch. It needs a durable task, explicit authority, observable progress, restart behavior, and evidence the parent can judge.

Calvin French-Owen gave the work its name

Then I read Calvin French-Owen’s “Small Models Have Arrived.” His distinction between “IQ 180” work and “token spewer” work named the split I had been feeling.

Some work needs the best available model because the answer is novel, ambiguous, or expensive to get wrong. Much more work needs a responsive worker that keeps pushing a known task forward.

Calvin’s articulation made the idea feel larger than my own token bill. I renamed delegate to Spewer, pulled it out of an internal project, refined its boundaries, and released it as open source.

The opportunity is not to make every model equally smart. It is to stop buying maximum intelligence for work that does not need it.

Small waste becomes infrastructure at company scale

Serial entrepreneur Suresh Batchu sharpened the operational version of this argument in a conversation. Engineers were asking models for the time and weather.

One weather question is trivial. Repeated across employees, agents, and automated loops, trivial requests become a material inference workload.

This matters because the terminal is becoming a harness interface. The shell will remain underneath, but an agent will increasingly decide which commands, models, and tools should do the work.

If that harness sends every request to its smartest model, token waste becomes an architectural choice. Cost control must sit in the path where work gets classified and dispatched.

Delegation follows from four first principles

Four constraints make delegation useful without replacing the harness. Together, they define Spewer’s product boundary.

  1. 01

    Harness preference is real

    People choose Codex, Claude Code, Kimi, or another harness for the complete experience. A cost tool should not force a migration.

  2. 02

    Work has different shapes

    A bounded objective with checkable output can leave the frontier turn. An ambiguous decision with broad context should stay.

  3. 03

    Price belongs to a task class

    No model is simply “best.” A model is a good choice when it meets the quality bar for a recurring class of work.

  4. 04

    The parent keeps judgment

    The worker returns evidence. The frontier harness accepts, rejects, refines, or retries the result before answering the user.

Spewer sits between two pluggable ends

Spewer does not replace the harness on the left or the worker on the right. It owns the durable delegation between them.

The left adapter asks Spewer for live capability cards. Those cards describe each worker’s model, tools, network access, and current specialization.

Spewer snapshots the selected capsule before accepting a task. It then journals the task, leases capacity, and invokes either Codex App Server or Ollama through an engine adapter.

The worker can run in the foreground or continue after the frontier turn ends. Spewer preserves accepted work across service restarts and returns a typed receipt when the task becomes terminal.

That receipt records the observed model, token categories, tool count, wall time, capsule revision, skill identity, artifacts, and verification. Missing provider facts remain missing instead of becoming zero.

The same harness can sit on both sides

Codex can be the frontier on the left while Codex App Server runs Luna on the right. The user stays in one experience, but the delegated turn uses the cheaper model family.

This is the key abstraction: Spewer’s protocol is not a provider selector. It creates a durable task outside the parent turn, then returns evidence through the parent’s adapter.

Qwen3 proves the other direction. An Ollama capsule can run an open-weights model behind the same task protocol, journal, capability lookup, and receipt.

A skill can turn a cheap generalist into a specialist

A generic capsule advertises broad bounded work. Binding a SKILL.md changes that capsule to specialized without restarting Spewer.

The frontier discovers the new state through live capability lookup. New tasks receive an immutable skill snapshot, so the receipt can identify the exact instructions that shaped the worker.

This changes the economics of repeat work. The expensive model explores and crystallizes the method; a cheaper model follows that method on later tasks.

Pareto IQ turns model routing into evidence

A single intelligence score cannot tell me which model should handle a task. I need verified quality and actual cost for comparable work.

Spewer calls this comparison Pareto IQ. Each plot-ready point keeps its model, derived cost, checks passed, checks attempted, and price-configuration hash.

The denominator matters. A worker that passes two of two checks is not equivalent to one that passes two of ten. The task class matters too: a parser edit and an open-ended architecture review do not belong on the same curve.

Version 0.2 implements the receipt data, price provenance, comparison guard, and plot-ready telemetry library. It does not yet ship a polished spewer pareto CLI report.

That boundary keeps the savings claim honest. I can say Spewer moves routine work off Sol in my workflow. I will publish a percentage only after repeated, comparable task classes produce it.

My frontier model now acts more like a manager

I keep frontier models on work where their judgment changes the outcome. I delegate work where the objective, authority, and acceptance checks fit in a small contract.

Keep at the frontier

  • Architecture with ambiguous tradeoffs
  • Exploration across unfamiliar systems
  • Security-sensitive decisions
  • Final review and user-facing judgment

Spew to a worker

  • Repository scans and inventories
  • Summaries and first-pass research
  • Test triage with explicit checks
  • Repeat procedures with bound skills

Foreground delegation gives me an answer in place. Detached delegation returns a task ID, lets the work continue, and gives me watch, check, respond, and cancel.

The separation also improves attention. Sol keeps the broad conversation and hard decision. Luna or Qwen3 receives only the projected task and returns a bounded result.

The shell is becoming a worker behind the harness

The terminal will not stop running commands. The interactive surface above those commands is becoming a harness that can plan, ask, delegate, and resume.

That shift creates a new systems question: which work deserves frontier inference? A model dropdown should not answer it.

Spewer’s bet is small. Keep the interface you prefer, give routine work a cheaper path, and make every handoff return enough evidence to judge.

Install it without changing harnesses

Homebrew installs spewer and its short alias, spu. The setup command prepares Luna, the Codex delegation skill, and the detached service.

# Install the release
brew install modiqo/tap/spewer

# Prepare the default Luna worker
spewer install

# Prove the path
spewer ask "Return only the sum of 17 and 19."
